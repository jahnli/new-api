# /changelog — 变更日志生成

根据 git 变更自动生成语义化 changelog 条目。

## 触发条件

- `/changelog`、`生成 changelog`、`更新 changelog`、`写 changelog`
- 或 commit 前自动触发

## 上游合并排除规则（硬规则）

以下内容**一律不得**新增或合并到 `changes/CHANGELOG.md`，也不得在 `changes/details/` 创建对应详情文件：

- `git fetch`、`pull`、`merge`、`rebase`、`cherry-pick` 等上游同步操作
- 合并提交、上游 commit 列表、合并统计、冲突文件、冲突解决策略和验证结果
- 直接来自 upstream 的功能、修复、依赖升级、文档调整或文件增删
- 仅为保持本地现有二开行为而做的冲突适配
- 文件名或标题类似 `upstream-merge`、`merge-upstream`、`sync-upstream` 的记录

禁止创建诸如“合并 upstream/main 的 N 个提交”一类条目。`changes/CHANGELOG.md` 只追踪本地相对上游新增或改变的二开行为。

如果上游合并期间额外实现了一个独立的本地功能或改变了本地业务行为，只记录该功能本身；说明中不得包含上游 commit、合并过程、冲突数量或同步背景。

## 工作流程

### 第 1 步：获取变更信息

```bash
# 查看暂存区变更（优先），若无暂存则查看工作区
git diff --cached --name-status 2>/dev/null || git diff --name-status

# 若上面为空，查看未跟踪文件 + 工作区变更
git status --porcelain
```

若变更仅涉及以下目录/文件，**无需生成 changelog**，直接告知用户跳过：

- `changes/`、`.cursor/`、`.agents/`、`.claude/`、`.codex/`、`.githooks/`、`.github/`
- `package-lock.json`、`bun.lockb`
- `AGENTS.md`、`CLAUDE.md`、`README.*.md`、`LICENSE`
- 纯格式化/注释变更

### 第 2 步：分析变更语义

读取每个变更文件的 diff 内容，理解改了什么、为什么改，用一句简洁中文概括。示例：

- "LDAP 登录时飞书同步改为同步调用，确保首次登录响应即包含头像"
- "移除 GitHub、Discord 等 OAuth 登录：删除后端提供商实现、前端界面及翻译"
- "侧边栏背景色改为透明（所有主题预设、明暗模式）"

这一步产出的只是**功能概括**。实现细节（具体文件里改了什么、参数值、样式数值、字段名）留给第 6 步的详情文件，不要塞进这一句。

### 第 3 步：检查是否需要合并

**在确定编号之前**，先读取 `changes/CHANGELOG.md` 的完整内容，判断本次变更是否与已有条目属于同一界面或同一功能。

判定标准（满足**任意一条**即视为同一功能）：

- 修改了已有条目详情列中的同名文件
- 修改了已有条目的详情文件中列出的文件
- 修改的文件路径与已有条目属于同一个 feature 目录（如 `src/features/auth/`、`src/features/home/`）
- 从 diff 内容判断是对同一功能的持续优化或补充

### 第 4 步：执行合并或新增

#### 合并（同一功能）

找到已有条目后，更新而非新增：

1. 更新已有条目的"说明"列，**只改功能概括**——一句话说清现在这个功能是什么。不要用分号把历次改动串成一长串，不要写入参数值、样式数值、列名清单等实现细节。
2. 更新已有条目的"日期"为当前日期
3. 把本次改动的实现细节写进该条目的详情文件（见第 6 步格式）。若该条目尚无详情文件，先按第 6 步创建，再把详情列改为 `[详情](details/xxx.md)`
4. 详情文件的"涉及文件"列表追加本次新增/修改的文件及其说明

示例：已有条目 `010 | 2026-06-19 | Toast 关闭按钮位置由左上角改为右上角 | ...`，本次又修改了 toast 相关样式，则更新为：

```
| 010 | 2026-06-23 | Toast UI 优化：关闭按钮移至右上角，状态色改为固定配色 | ... |
```

首次改动是"按钮位置"、本次是"状态色"，说明列合并为功能级概括即可，无需保留每条明细；明细进详情文件。

#### 新增（不相关功能）

仅当本次变更与 CHANGELOG.md 中**所有已有条目均不相关**时，才新增编号。

### 第 5 步：确定编号（仅新增时）

```bash
# 读取当前最大编号
rg "^\\| (\\d+) " changes/CHANGELOG.md --no-line-number -r '$1' | sort -n | tail -1
```

新编号 = 最大编号 + 1，用 3 位零填充（如 `034`）。

### 第 6 步：写详情文件（默认）

**CHANGELOG.md 的说明列只放功能概括，实现细节一律放详情页。** 因此新增条目默认创建 `changes/details/{编号}-{短标识}.md`：

```markdown
# 一句话标题（功能级，不含实现细节）

**日期**: YYYY-MM-DD

## 涉及文件

- `path/to/file1` — 具体改动说明
- `path/to/file2` — 具体改动说明

## 变更说明

（可选的实现细节：参数值、样式数值、字段名、列顺序、i18n 语言数等。
 说明列里写不下的内容都写在这里，不要反过来堆进表格。）
```

短标识用英文 kebab-case，提取自说明中的核心关键词，如 `ldap-sync-fix`、`remove-oauth`。

然后在 CHANGELOG.md 详情列写：

```
| 034 | YYYY-MM-DD | 一句话中文说明 | [详情](details/034-ldap-sync-fix.md) |
```

#### 例外：改动足够小时可直接写文件路径

仅当**同时满足**以下条件时，才不建详情文件、在详情列直接写文件路径：

- 涉及文件 ≤2 个
- 说明本身就能在一行内讲完，没有任何实现细节需要另处存放

```
| 036 | YYYY-MM-DD | 系统公告弹窗宽度由 26rem 加大到 36rem | `web/src/components/notification-popover.tsx` |
```

只要说明里出现了分号串起来的多个改动点，就说明细节已经超标——建详情文件。

### 第 7 步：写入 CHANGELOG.md

用 Edit 工具修改 `changes/CHANGELOG.md`（合并场景修改已有行，新增场景在末尾追加）。确保：

- 表格列对齐
- 编号 3 位零填充
- 日期格式 `YYYY-MM-DD`

### 第 8 步：添加变更到 git 暂存区

```bash
git add changes/CHANGELOG.md
# 若有详情文件
git add changes/details/{编号}-{短标识}.md
```

### 第 9 步：输出确认

向用户展示操作结果：

```
✅ changelog 已更新：

  操作: 合并到 #010（Toast UI 优化）
  说明: Toast 关闭按钮移至右上角、背景色微调

或

✅ changelog 已生成：

  编号: 034
  说明: LDAP 登录时飞书同步改为同步调用，确保首次登录响应即包含头像
  详情: details/034-ldap-sync.md（含 `controller/ldap.go`、`service/feishu_sync.go`）
```

## 关键规则

1. **所有说明文字必须是中文**
2. **编号必须 3 位零填充**（`001`、`012`、`134`）
3. **说明列只写功能概括，一句话（约 40–60 字）**，不写参数值、样式数值、列名清单等实现细节
4. **实现细节一律放详情页**；默认创建详情文件并在详情列写 `[详情](details/xxx.md)`
5. **仅当涉及文件 ≤2 个且说明一行可讲完时**，详情列才直接写文件名（用顿号分隔不用逗号）
6. **纯格式化/注释等无需记录的变更直接告知用户跳过**
7. **同一界面/功能的连续修改必须合并到已有条目，不要新增编号**；合并时说明列做功能级概括，明细追加进详情文件
8. **仅在变更与所有已有条目均不相关时，才新增编号并在末尾追加**
9. **上游同步、合并过程和纯上游改动永不记录；不得创建 upstream-merge 详情文件**

## 说明列写法

说明列是给"查这条改了什么功能"用的索引，不是改动清单。

| 该写 | 不该写 |
|------|--------|
| "渠道创建与编辑由侧边抽屉改为居中弹框" | "…头部、供应商选择区、表单与页脚纵向分区，状态徽章与供应商切换按钮移入头部操作区" |
| "用户头像改用 avatar_url 字段" | "…后端 API 下发 avatar_url，前端头像组件优先展示图片、无图时回退首字母" |
| "模型广场与分组定价优化" | "…新增分组 × 供应商倍率配置与统一计费优先级、定价响应加密、超级管理员入口…" |

判断方法：如果一个分句删掉后，读者仍能知道"这个功能变成了什么样"，它就属于详情页。

## 合并与新增规则（详细）

| 场景 | 操作 |
|------|------|
| 改的是已有条目中的同名文件 | **合并**：更新功能概括、日期、详情文件 |
| 改的是已有条目详情文件中列出的文件 | **合并**：更新功能概括、日期、详情文件 |
| 改的文件与已有条目同属一个 feature 目录 | **合并**：更新功能概括、日期、详情文件 |
| 从 diff 判断是对同一功能的持续优化 | **合并**：更新功能概括、日期、详情文件 |
| 变更与所有已有条目均无关联 | **新增**：确定编号、追加行、按第 6 步建详情文件 |

**合并时不需要递增编号，原编号不变。**

## 存量条目的整理

若发现已有条目的说明列已经堆了实现细节（多分句、超长单元格），按同一原则就地整理：把细节原样迁入该条目的详情文件（追加 `## 自 CHANGELOG 说明列迁入` 段落），说明列改写为功能概括。整理只做搬家，不改写、不丢弃任何事实点。

## 编号格式

CHANGELOG.md 中编号列统一 3 位零填充：`| 001 |`、`| 012 |`、`| 134 |`。

读取最大编号时排除可能的重复（如同一编号出现多次），取最新一行的编号。

## 短标识命名

详情文件的短标识从说明中提取核心关键词，用英文 kebab-case：

- "LDAP 登录时飞书同步改为同步调用" → `ldap-sync`
- "修复侧边栏选中项悬停时文字颜色被覆盖" → `sidebar-hover-color`
- "移除邀请人/邀请码功能" → `remove-invitation`

控制在 3-5 个单词，不要过长。
