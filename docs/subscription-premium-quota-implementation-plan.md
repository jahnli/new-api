# 订阅高阶模型额度限制实施方案

版本：2.1  
日期：2026-09-15  
状态：代码已实现，编译及前端静态检查通过；数据库验证与部署验收待完成。未修改运行配置，默认比例 100%，限制初始关闭

## 1. 实施目标与范围

在现有订阅额度机制上增加高阶模型消费上限。**不新增数据库表，仅新增 4 个字段**，复用现有订阅预扣、结算、退款和配置存储。

| 项目 | 实施规则 |
| --- | --- |
| 订阅总额度 B | 沿用当前订阅的总额度 |
| 高阶比例 C | 系统初始默认 **100%**，管理员可修改默认值 |
| 用户单独配置 | 管理员可设置用户覆盖值；留空继承系统默认 |
| 比例范围 | 0～100 的整数；0 与未设置必须区分 |
| 高阶消费 | 同时占用订阅总额度和高阶限额 |
| 普通消费 | 只占用总额度，可使用全部剩余总额度 |
| 高阶模型定义 | 在订阅管理中拉取已有模型，由管理员多选配置 |
| 生效时间 | 保存后对新请求立即生效，既有占用不清零 |
| 实际费用超出预估 | 允许实际高阶费用超过分类上限，完整记账，后续新请求受限 |
| 钱包回退 | 沿用用户计费偏好和套餐的钱包回退设置 |
| 订阅范围 | 当前按每用户一份有效、有限额度且有重置周期的订阅实施 |

高阶额度是总额度的一部分，不单独预留给高阶模型。C 不参与价格计算，不改变模型价格、分组倍率或计费表达式。

默认 100% 时仍累计高阶占用，便于管理员中途调低比例后立即按已有占用判断剩余额度。

本期不开发多订阅共享池、跨订阅拆扣、无限额度规则或独立历史周期余额账本。上线前核对实际订阅是否符合实施范围；发现例外时报告并处理，不自动选择任意订阅代替判断。

## 2. 额度计算

### 2.1 统一口径

沿用现有 `AmountUsed` 包含未结算预扣的含义，高阶计数也采用同一口径。

| 符号 | 对应数据 | 含义 |
| --- | --- | --- |
| B | `AmountTotal` | 当前订阅总额度 |
| U | `AmountUsed` | 所有模型当前占用，包含预扣 |
| H | `premium_amount_used` | 高阶模型当前占用，包含预扣 |
| C | 用户覆盖或系统默认 | 生效比例 |
| L | 计算值 | 高阶额度上限 |

```text
L = floor(B × C / 100)
总可用额度 = max(0, B - U)
高阶可用额度 = max(0, min(B - U, L - H))

普通请求预扣 P：B - U >= P
高阶请求预扣 P：B - U >= P，且 L - H >= P
```

额度控制以主库计数为准，不从消费日志实时求和，不依赖 Redis 单独记账。

所有金额内部使用 quota 整数。计算 L 时先校验 B 非负、C 在 0～100，再使用避免乘法溢出的整数表达式，例如 `(B / 100) * C + ((B % 100) * C) / 100`。展示时复用项目的额度与货币换算规则，不把 quota 直接视为人民币。

### 2.2 示例

假设 B=100 元，管理员为该用户单独设置 C=30%。

| 情况 | 总占用 U | 高阶占用 H | 总可用 | 高阶可用 |
| --- | ---: | ---: | ---: | ---: |
| 尚未消费 | 0 | 0 | 100 | 30 |
| 高阶消费 20 元 | 20 | 20 | 80 | 10 |
| 再使用普通模型消费 75 元 | 95 | 20 | 5 | 5 |
| 高阶占用 30 元，总占用 40 元 | 40 | 30 | 60 | 0 |

普通模型可以用完 100 元。高阶未使用的限额不会阻止普通模型消费。

### 2.3 预估误差

高阶剩余 1 元，请求预扣 0.5 元、实际费用 2 元时：

1. 预扣时同时占用总额度和高阶额度各 0.5 元。
2. 结算时按实际 2 元更新占用；高阶 H 可以超过 L。
3. 高阶可用显示 0，后续新的订阅高阶预扣失败。
4. 根据原计费偏好和套餐规则尝试钱包回退，或返回额度不足。

不增加最大费用预留或流式截断。多笔在途请求的实际差额可能累积，因此不承诺固定的超出金额上限。

这里只放宽高阶分类上限的结算检查。**当前周期总额度补扣仍保留原有约束**：若总额不足导致结算失败，保留已占用额度和待处理结算目标，不把已发生消费自动退款，也不自动改为另一资金来源扣款。

## 3. 高阶模型配置

### 3.1 管理入口

在订阅管理页增加“高阶模型额度设置”，包含：

- 是否启用高阶额度限制。
- 默认比例，初始 100%。
- 已有模型的搜索、多选和刷新。
- 已选模型及选择数量。
- “修改影响新请求，已占用额度不清零”的说明。

模型集合对所有订阅用户统一生效。套餐不单独维护集合，用户仅覆盖比例。首版不支持手写模型名、通配符、正则或按价格自动分类。

### 3.2 模型候选与计费身份

选项复用现有模型目录和渠道具体模型来源，以元数据补充展示名称、供应商等信息，最终保存有效计费模型名称。

实现要求：

1. 现有 `model.Model` 支持前缀、后缀和包含匹配。候选必须展开成实际配置的具体模型，不能把规则名称直接保存为计费身份。
2. 候选生成与请求执行复用现有计费名解析规则。`relay/helper/price.go` 已会解析计费身份，运行时使用 `GetBillingModelName()`；不得在前端另写一套别名转换。
3. 多个对外名称归一为相同计费名时合并选项，展示关联名称，说明选择会覆盖这些名称。
4. 按有效计费名精确匹配，不依据数据库模型 ID、展示文案、价格高低或上游渠道名判断。
5. 新增模型默认未选中。已选模型停用或从候选消失时保留选择并标记不可用，刷新不能静默移除配置。
6. 拉取失败保留原选择并显示错误，不能按空列表保存。

现有 `/api/models/` 管理接口使用 `RootAuth`，订阅管理使用 `AdminAuth`。增加订阅管理专用只读选项接口，复用后端查询能力，不降低原模型管理接口权限。

### 3.3 分类快照

在有效计费名确定之后、订阅预扣之前计算：

```text
is_premium = 高阶模型集合包含有效计费模型名
需要检查高阶限额 = enabled && is_premium
```

首次启用后持续按当时模型集合记账；关闭开关只停止分类限额检查，仍记录高阶占用。重新启用不清零。首次启用以前的请求不补算高阶占用。

请求保存分类快照，结算和退款使用原快照。管理员修改模型集合，不重新分类历史请求。

渠道重试仅改变上游映射、计费身份不变时沿用快照。确实改变计费身份的重试，在发送前重新校验并原子调整该次未消费预留的分类；不能覆盖已经产生实际消费的分类。

## 4. 数据设计

### 4.1 新增字段清单

| 现有模型 | 新字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| `User` | `subscription_premium_percent` | 可空整数，Go `*int` | NULL 继承默认；0 为显式 0%；仅管理员写入 |
| `UserSubscription` | `premium_amount_used` | int64 | 当前周期高阶占用，包含预扣 |
| `UserSubscription` | `quota_reset_version` | int64 | 从 1 开始，每次实际重置递增 |
| `SubscriptionPreConsumeRecord` | `billing_context` | TEXT | 保存分类、周期版本、记账状态和幂等信息 |

高阶上限 L 按需计算，不保存为列。总额度和总占用继续使用现有字段。不拆分新的“已结算”和“预留”计数字段。

### 4.2 全局配置

复用现有 option/config 持久化机制，保存一份整体配置：

```json
{
  "enabled": false,
  "default_percent": 100,
  "model_names": [],
  "version": 1,
  "first_enabled_at": 0
}
```

初始关闭，管理员选好模型后启用。首次启用时设置 `first_enabled_at`，后续不覆盖。

配置通过版本比较原子保存，模型列表、比例和开关不会出现半更新。模型名去重并进行服务端合法性校验，配置缺失时才应用初始默认值，不能覆盖管理员已有设置。

立即生效以数据库提交为边界：保存后进入准入的新请求读取新配置；已经取得旧快照并开始准入的请求可以完成。首版在既有主库预扣事务内读取配置和用户覆盖值，缓存只用于展示或可验证版本的快照，不能仅等缓存 TTL 后才生效。

### 4.3 用户比例

生效顺序：

```text
用户字段非 NULL → 使用用户覆盖
用户字段为 NULL → 使用系统默认
系统配置未初始化 → 默认 100
```

不把管理员字段放入用户可自行编辑的偏好 JSON。普通个人设置接口和通用更新路径使用明确字段白名单，不能批量回写此字段。

并发编辑使用“预期旧值 + 条件更新”，不新增用户版本列。NULL 使用对应的 `IS NULL` 条件，不能和 0 混用。更新后刷新用户展示缓存；扣费以主库值为准。

### 4.4 请求计费上下文

`billing_context` 使用 Go 结构体，通过 `common.*` 序列化为 TEXT，不依赖数据库特有的 JSON 更新函数。

核心结构示例：

```json
{
  "schema_version": 1,
  "billing_model_name": "configured-model-a",
  "is_premium": true,
  "quota_reset_version": 1,
  "accounted_quota": 5000,
  "phase": "reserved",
  "revision": 1
}
```

| 内容 | 语义 |
| --- | --- |
| `billing_model_name` | 本次有效计费身份 |
| `is_premium` | 本次分类记账快照；首次启用前的请求不追溯分类 |
| `limit_enabled`、`effective_percent`、`policy_version` | 本次准入配置快照，补充预扣继续使用原配置 |
| `quota_reset_version` | 原始扣费周期版本 |
| `accounted_quota` | 这条记录已经记账的净额 |
| `phase` | 预扣、结算待处理、已结算、已退款等状态 |
| `revision` | 同一记录单调递增的资金操作版本 |

预扣后净额是预扣合计；结算后是实际净消费；全额退款后是 0。调整统一传递“目标净额 + 操作版本 + 操作类型”，由模型层计算差额。

同版本同内容重复提交幂等返回；同版本不同内容报冲突；旧版本不得覆盖新状态。调用方重试必须复用原版本，不能每次重试重新生成版本。异步任务的版本和记录引用保存在现有任务私有 JSON 中。

待处理结算按需在上下文保存 `pending_target_quota` 与目标版本，失败原因保持为非秘密摘要。状态机阻止已结算记录被迟到的“预扣”重新打开；合法结算修正使用新版本。

现有 `request_id` 唯一键继续负责预扣幂等；旧 `PreConsumed` 字段保留原初始预扣语义。现有 `Status` 作为可查询的状态投影，与上下文同事务更新，便于清理任务筛选。所有依赖旧 `consumed/refunded` 字面值的调用处需要同步适配。

### 4.5 重置版本与任务引用

每次自动或手动实际重置，都将 `quota_reset_version` 递增，即使管理员选择“不推进下次重置时间”。仅修改 C、B、模型列表或功能开关不递增。

现有手动重置可能不更新 `LastResetTime`，所以不能仅用时间字段代替此版本。

异步任务在现有 `TaskPrivateData` JSON 内保存扣费记录 ID，结算时由记录找到订阅和周期，不增加任务数据库列。新同步请求通过现有 `RelayInfo`/资金来源对象传递同一引用。

## 5. 资金处理流程

### 5.1 预扣

1. 沿用现有价格引擎计算预扣 P，保留所有数量、时长、token 边界校验。
2. 在订阅准入事务中读取配置、用户覆盖和有效订阅，必要时完成周期重置。
3. 根据 `request_id` 查询既有记录，验证用户和请求归属并幂等返回。
4. 检查总可用；启用限制的高阶请求同时检查高阶可用。
5. 普通请求增加 U；高阶请求增加 U 和 H。
6. 写入分类、重置版本、预扣净额及状态，和计数更新整体提交。
7. 成功后才向上游发送请求。

订阅继续禁止信任额度旁路。事务失败必须完全回滚，不能只占用总额度或高阶额度的一项。

### 5.2 补充预扣

发送前参数或数量变化需要增加预扣时，更新同一记录的目标净额并再次检查余额。普通请求检查总额度，高阶请求在限制开启时同时检查分类额度。

订阅的 `extraReserved` 纳入持久化净额，退款时一次退还实际可退金额。不能保留“记录退款后再按额外预留减一次”的重复路径。

### 5.3 结算

锁定订阅和扣费记录，校验版本与状态：

```text
差额 D = 实际目标净消费 A - accounted_quota
```

当前周期内，普通请求更新 `U += D`；高阶请求同步更新 `U += D`、`H += D`。资金提交后将记录净额改为 A。

- 最终结算不因 H 超过 L 拒绝补扣。
- 当前周期总额不足的正差额保留原约束：资金变更不提交，保存待处理目标，记录失败。
- A 等于预扣时，也要提交“已结算”状态，不能只因差额为 0 提前返回。
- 资金已提交而令牌额度调整失败，不能再次扣订阅资金或自动退回已发生消费；保留现有分步提交保护。
- 配额转换复用 `Quota*Checked` 与现有饱和审计。累计值另行检查 int64 加减溢出，不能通过溢出形成负扣费。

### 5.4 退款

未产生应付费用的失败请求退还记录中实际可退净额；已结算请求的合法退款通过降低目标净额实现。

分类使用原快照。当前周期内，高阶退款同时减少 U、H；普通退款不改 H。退款金额不得超过记录可退净额，不用简单钳制为 0 掩盖重复退款或状态错误。

记录状态、净额和额度计数在同一事务提交。模型内部使用接收现有事务的方法，避免退款事务里再开启独立资金事务。

### 5.5 异步任务与兼容路径

必须接入以下路径：

- `SubscriptionFunding` 的预扣、结算、退款。
- `BillingSession` 的补充预扣、零差额结算及退款。
- 无 BillingSession 时 `PostConsumeQuota` 的订阅兼容分支。
- 任务失败退款、实际用量重算和后续修正。

任务持久化记录引用后才能交给异步处理。退款成功但任务状态保存失败时，重试通过扣费记录幂等返回，不能再次退款。

宿主统一控制分类，不新增任务插件协议字段。若实施涉及插件宿主 API/运行时，先完整阅读 `docs/plugin-api/v1.md` 及相关约定。

### 5.6 并发与锁顺序

MySQL/PostgreSQL 调用 `lockForUpdate(tx)`；SQLite 使用事务及带余额/版本条件的更新。检查 `RowsAffected`，出现写竞争按有界方式重试。不能先读余额再无条件覆盖整行。

统一采用“用户 → 订阅（按 ID）→ 请求记录（按 ID）”的修改锁顺序。需要先从记录定位订阅时，可先只读获取归属，再按顺序加锁并复核；归属已变更则重试。配置保存不在持有这些业务锁时反向申请锁。

替换、取消、到期与结算先锁用户再修改订阅；只修改订阅的重置路径不反向获取用户锁。事务内不发起上游网络调用。请求唯一键冲突回滚，不能在 PostgreSQL 已失败事务内继续查询并假装成功。

## 6. 重置及管理操作

| 操作 | 总额度和高阶额度行为 |
| --- | --- |
| 调高用户比例 | 增加高阶上限，保留 H |
| 调低用户比例 | 保留 H，低于已占用时可用显示 0；已有预扣可以继续结算 |
| 恢复继承 | 覆盖设为 NULL，按当前默认值判断新请求 |
| 修改系统默认 | 只影响继承用户 |
| 修改高阶模型集合 | 只改变新请求分类，历史记录不重算 |
| 增加 B | 同步提高计算出的 L，U/H 不变 |
| 减少 B | 沿用总额增减限制，L 同步减少，H 不清零 |
| 自动或手动重置 | 同事务清零 U/H，按现有规则更新 B，递增重置版本 |
| 取消或到期 | 不接受新预扣，保留旧请求结算与退款能力 |
| 关闭再开启限制 | 不清零 H，不改变重置版本 |

### 6.1 跨周期处理

结算或退款时，比较记录的重置版本与订阅当前版本。

- 版本相同：按当前周期资金流程更新 U/H。
- 版本不同：更新该请求净额、状态和消费/退款日志，不修改当前周期 U/H。

旧周期已结束，旧请求退款不能增加新周期余额；旧请求后结算也不扣新周期额度。实际费用及差额继续留在请求记录和消费统计中。

本方案不维护独立历史周期余额，不在旧周期结束后重新检查旧周期剩余总额。旧请求已在原周期完成准入，后续只保留实际记账结果。若需要历史账期可用余额或按旧周期追补余额，应另行设计，不在本次增加数据结构。

### 6.2 同套餐替换

当前绑定替换存在继承总占用的行为，必须同步继承高阶占用：

1. 在同一事务锁定旧订阅、新订阅及受影响记录。
2. 将当前周期的 U/H 继承到新订阅。
3. 将仍可结算、修正或退款的当前周期记录更新为新订阅归属及对应重置版本；包含已经结算但仍允许修正的记录。
4. 保留原订阅引用的审计信息，任务通过记录查询当前归属。
5. 已属于关闭周期的记录不转移为当前周期。

明确授予新周期额度的操作则按重置规则执行。替换与新预扣串行，防止两份订阅同时消费继承额度。

### 6.3 删除和清理

存在未完成或仍可调整的记录时，禁止硬删除其订阅归属；可取消订阅并保留记录。

原预扣清理任务按 7 天清理，需改为排除未完成、待处理和活动任务引用记录。终结记录只有在退款/修正窗口结束后才能归档，归档后仍保留防止重放的唯一摘要或等价约束。上线版本未建立归档能力时保留记录，不按时间盲删。

## 7. 接口设计

沿用 `{success, message, data}` 响应封装。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/subscription/admin/premium-policy` | 获取全局设置及版本 |
| PUT | `/api/subscription/admin/premium-policy` | 原子保存全局设置 |
| GET | `/api/subscription/admin/premium-model-options` | 获取已有模型选项 |
| GET | `/api/subscription/admin/users/:id/premium-policy` | 获取用户覆盖及生效值 |
| PUT | `/api/subscription/admin/users/:id/premium-policy` | 设置或清除用户覆盖 |

### 7.1 全局保存

```json
{
  "enabled": true,
  "default_percent": 100,
  "model_names": ["configured-model-a", "configured-model-b"],
  "expected_version": 1
}
```

模型名只是结构示例，不预置具体高阶模型。版本不符返回 HTTP 409，刷新后重试，不能覆盖其他管理员的修改。

### 7.2 用户保存

```json
{
  "percent_override": 30,
  "expected_percent_override": null
}
```

表示“原先继承，现在改为 30%”。恢复继承提交 `percent_override: null`，预期旧值传当前覆盖。

两个字段均必填，NULL 与字段缺失必须区分。后端采用能表示字段存在性的 DTO，不用单个普通指针同时表达两种含义。并发旧值不符返回 HTTP 409。

### 7.3 额度读取

扩展现有 `/api/subscription/self` 和管理员用户订阅查询，增加只读对象：

```json
{
  "premium_quota": {
    "enabled": true,
    "effective_percent": 30,
    "percent_source": "user",
    "premium_amount_used": "120000",
    "premium_limit": "300000",
    "premium_available": "180000",
    "over_limit_quota": "0",
    "tracked_since": 1789344000
  }
}
```

示例数值是 quota，不是人民币。新增 int64 金额字段使用十进制字符串，前端通过统一格式化适配层处理，不能无界转为 `Number`；旧接口字段类型保持兼容。

`premium_available` 已同时考虑总余额。`tracked_since` 表示分类开始记录时间，不是周期 ID。接口不提供未维护的“高阶已结算/预留”拆分值。

### 7.4 权限与错误

所有配置写接口使用服务端管理员权限检查。用户本人只读自己的生效比例及额度，不能通过个人设置接口覆盖管理员字段。复用既有会话、CSRF 与权限中间件；实施若触及认证相关流程，先按项目要求阅读适用 OWASP 指引。

高阶额度不足使用独立结构化原因 `subscription_premium_quota_insufficient`，归入现有可按偏好回退的额度不足类别，不能靠字符串匹配识别。

数据库/配置读取失败是系统错误，不伪装成额度不足，不触发钱包扣款。总额度不足保留既有错误语义。

## 11. 迁移、上线与回退

### 11.1 数据初始化

- 用户覆盖初始化 NULL。
- 高阶占用初始化 0，保留已有 B 和 U。
- 订阅重置版本初始化 1。
- 旧预扣上下文允许为空，不根据当前模型集合追溯分类。
- 全局配置不存在时初始化默认 100%、空模型集合、关闭状态。

初始化通过明确迁移版本或缺失状态识别，只执行一次。重复启动不能把合法的 0% 覆盖成默认值，也不能清零已经存在的 H。

新增字段使用通用整数和 TEXT。布尔开关存在配置 JSON 中，不引入布尔数据库默认标签。JSON 编解码走 `common.*`。

### 11.2 上线步骤

1. 备份主库与配置，确认目标用户满足单订阅、有限额度和定期重置前提。
2. 部署新增字段与兼容代码，限制保持关闭；确认所有扣费节点升级完毕。
3. 切换前暂停新订阅预扣，排空旧同步请求并盘点活动任务。
4. 旧任务能明确识别当前归属的，补齐记录引用并验证没有重复记入 U；无法识别周期的任务先完成或逐项处理，不能猜测退款归属。
5. 新节点开始使用扩展记录，恢复订阅预扣。
6. 管理员选择高阶模型并启用，默认 100%，记录首次启用时间。启用后新高阶预扣开始累计 H，旧请求不补算。
7. 核对高阶占用、钱包回退、实际超出、待处理结算和重置后的余额。

首次启用 H 从 0 起算，但原总占用不变。随后修改比例、重启或关闭再启用均不清空 H。

### 11.3 回退

优先关闭分类限额开关，保留新版本记账与在途结算。不开启旧节点与新节点混合写入，也不通过删字段回退。

如必须降级程序，先停止新订阅请求、结清或冻结在途资金操作并核对 U/H，再使用已验证兼容新记录的版本。旧版本不理解高阶占用，不能直接接回写流量。
