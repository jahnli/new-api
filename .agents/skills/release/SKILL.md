# 全自动发布

## 执行约定

- 创建、编辑或解释本技能时不执行发布。用户调用 `/release` 或明确要求执行全自动发布，即授权一次 Docker 发布及其成功后的 1Panel 更新、强制拉取和重建，无需阶段间再次确认。
- 执行前完整读取 [docker-publish](../docker-publish/SKILL.md) 和 [1panel-deploy](../1panel-deploy/SKILL.md)，按各自的接口、鉴权、运行定位及核验规则执行；本技能负责串联阶段和汇总结果。
- 默认发布仓库 `jahnli/new-api` 的 `docker-publish.yml`，部署 `local` 节点的 `ai-gateway` 编排和容器，目标镜像仓库为 `jahnlis/ai-gateway`。用户指定值优先。
- ref 使用用户指定的远端分支或标签，否则查询远端默认分支；reason 使用用户原文，否则为 `Manual Docker Publish via agent`。仅发布远端代码，不自动提交、推送或创建标签。
- Docker 阶段产出的实际版本标签自动传给 1Panel，不再询问标签，不使用 `latest`，不从本地版本、SHA 或运行日期推算。
- 始终按“预检 → Docker 发布 → 1Panel 更新 → 核验 → 汇总”顺序执行，任何阶段失败或状态无法确认时停止后续写操作并交付已有结果。
- 凭据只在请求进程中读取，不展示 `.1panel.local.json`、`.env`、签名、完整响应、Compose 或未经脱敏的日志。

## 1. 预检

1. 按 Docker 技能检查 `gh` 登录、远端 ref、默认分支及目标 ref 的工作流定义和输入，确定可执行发布。
2. 按 1Panel 技能检查凭据来源及忽略规则，以只读 API 查询确认目标编排和容器唯一、路径可用、目标镜像可安全修改。记录原镜像、容器 ID、镜像 ID、运行状态；原 Compose 和 env 仅保留于内存。
3. 记录应用访问地址和状态接口。默认应用地址为 `http://ai.semi-tech.com:3002`，状态接口为 `http://ai.semi-tech.com:3002/api/status`，面板 API 为 `http://ai.semi-tech.com:8080/api/v2`。自定义部署时依据用户配置和实际端口/域名确认地址，不沿用默认地址或猜测面板登录入口。
4. 缺少凭据、工作流不可用或目标不明确时，在触发构建前报告阻塞。仅询问无法从默认值或配置确定的必要参数。
5. 简述远端 ref、部署目标及重建可能造成的短暂中断，然后直接执行。

## 2. 发布 Docker 镜像

1. 严格执行 Docker 技能：记录触发前时间和已有运行 ID，触发一次，定位本次唯一运行，轮询同一运行直至完成。
2. 记录 `run-id`、运行链接、`headBranch`、`headSha` 和 `conclusion`。仅 `conclusion == success` 允许继续。
3. 从本次运行日志中的版本、镜像标签和推送完成记录核实完整版本标签及镜像仓库，保存实际发布的完整镜像引用。
4. 若命名空间脱敏，仅当已核实的标签及远端工作流发布配置足以证明镜像发布到目标仓库时，才可组装完整部署镜像；否则报告“构建成功，部署阻塞：目标镜像未核实”。
5. 实际发布仓库与部署目标不一致、标签无法核实或缺少推送完成证据时，不更新 1Panel，不擅自替换镜像仓库。

## 3. 自动更新 1Panel

1. 将上一步核实的完整版本镜像作为唯一部署目标。更新前重新查询编排和容器；若原配置已被其他操作修改，停止并报告冲突，避免覆盖。
2. 按 1Panel 技能仅修改目标服务的镜像，保留其余服务、卷、env 和 Unicode 内容，记录更新前镜像及容器/镜像 ID。
3. 生成唯一 `taskID`，提交一次编排更新，`forcePull: true`；本技能调用包含强制拉取和重建，即使当前标签相同也执行。
4. 轮询同一任务，最多等待 10 分钟；必须确认任务 `Success`、镜像拉取成功、容器 `Recreated` 和 `Started`。
5. 请求超时或结果不明时先查询已提交任务及容器，不重复提交。失败时报告现状，不自动重跑或回滚。

## 4. 核验与完成判定

按 1Panel 技能重新查询配置、容器和应用状态，全部满足才报告“发布成功”：

- Compose 与容器 `Config.Image` 均为本次发布的目标镜像。
- 新容器 ID 与更新前不同；记录新旧镜像 ID，同标签镜像 ID 可以不变。
- 容器为 `running`；存在健康检查时为 `healthy`，无健康检查则明确注明；记录重启次数。
- 状态接口 HTTP 200 且 `success == true`；提供 `data.version` 时，依据已核实的构建版本规则核对，不能把标签与应用版本的格式差异直接认定为失败。
- 应用版本字段缺失时注明“应用未返回版本，已核对运行镜像”；有版本但无法证明与本次发布一致时报告“部署完成，版本核验未完成”，不宣称全部成功。

所有轮询单次等待不超过 30 秒，每 60 秒内给出简短进度。查询受阻或超时时返回已确认状态和链接，保留运行/任务 ID 供继续查询。

## 5. 最终交付

无论成功、失败或阻塞，最终中文回复均列出已核实的信息；缺失字段写“未核实”或“未执行”，不得编造。使用简短段落和列表：

```text
发布结果：成功 / 失败 / 阻塞 / 部署完成但核验未完成
Docker：结果；远端 ref；提交 SHA；完整版本镜像
构建详情：本次 GitHub Actions 运行链接（运行 ID）
1Panel：结果；节点与编排；任务 ID
容器：新短 ID；运行状态；健康状态；重启次数
应用：状态接口 HTTP 结果、success 和实际版本；版本核对结果
访问地址：已确认的应用地址
状态接口：已确认的状态接口地址
面板 API：本次实际使用的 API 地址（非登录入口）
```

- 地址和工作流链接使用可点击链接；不把 API 地址描述成面板登录地址。
- 失败或阻塞时追加停止阶段、脱敏原因、当前服务状态（无法查询则注明）、下一步所需操作。Docker 失败明确写“1Panel 未执行”；Docker 成功而部署失败明确分别列出两阶段结果。
- 返回原镜像作为排查参考；任何回滚均需另有授权并核实数据库迁移兼容性。

## 调用示例

- `/release`：发布远端默认分支，成功后自动部署并返回结果及地址。
- `/release ref=v1`：发布远端 `v1`，成功后自动部署并返回结果及地址。
- “全自动发布 v1，先发布 Docker，成功后更新 1Panel”：执行同一完整流程。
