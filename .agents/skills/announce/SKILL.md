# AI Gateway 功能更新与公司公告

将提交记录转成同事能理解的“更新了什么、有什么用、在哪里使用”。默认读者为公司全体员工，管理员和 API 接入人员的更新放在独立补充区。默认交付功能清单与公告草稿，不执行部署或发送。

## 确定版本范围

- 在用户当前指定的 ai-gateway 仓库执行，先读取适用的 AGENTS.md。不要硬编码机器路径、分支、公司名称或生产地址。
- 优先使用用户给出的旧版本和新版本，解析为完整提交 SHA；其次使用指定分支及日期。未指定时以当前 HEAD 为目标，并明确它只是代码版本。
- “最近一个月”默认从用户所在时区的当日向前推一个日历月，月末按目标月份最后一天截断；“上个月”表示上一个完整自然月。记录实际起止日期、时区、包含边界和取数时间，不用宿主机日期覆盖会话提供的用户日期。不要因近期无提交而悄悄改用最近一条提交的月份。
- 记录分支、目标 SHA、浅克隆状态及工作区状态。默认只分析已提交内容；有未提交修改时，读取固定目标版本，避免混入正在开发的功能。
- 已知生产部署 SHA 或镜像对应 SHA 时，以它限定“已上线”。仅有“公司部署了该项目”不足以推断当前 HEAD 已上线；无需因此阻塞代码清单，标注“已合入，线上待核实”。不读取部署凭据，也不因生成公告而触发部署。

## 收集及交叉核实

按以下思路选择 Git 命令，参数替换为已解析的实际值：

```text
git branch --show-current
git rev-parse HEAD
git rev-parse --is-shallow-repository
git status --short
git log TARGET --since-as-filter=START --until=END --format="%H %cI %s"
git log TARGET --first-parent --format="%H %cI %s"
git log BASE..TARGET --no-merges --format="%H %cI %s"
git diff --name-status BASE TARGET
git diff BASE TARGET -- relevant/path
git show TARGET:relevant/path
```

- 日期边界使用带时区的时间；有明确版本范围时，以版本差异为准，日期只是辅助。选择日期窗口开始前的主线提交作为 BASE，并确认它是 TARGET 的祖先。提交时间乱序或缺少历史时说明范围限制，不伪造完整覆盖。
- 主线日志用于确认何时合入；同时检查 `BASE..TARGET` 的完整可达历史，包含合并带入的上游提交，不能仅用 `--first-parent`、作者、`feat` 前缀或提交日期筛选功能。旧日期提交在本期首次合入也可能属于本期；窗口内提交但基线已包含的内容不算新增。
- 读取 `changes/CHANGELOG.md` 及相关详情作为线索；该文件只记录本地二开，且条目会累积多个月的变化，不能直接把日期命中的整条内容当作本月新增。
- 每项入选更新至少核对提交差异与目标版本中的入口/实现；对照 BASE 判断新增、优化、修复或行为调整。合并提交的标题不是功能证据，已回退、被后续覆盖或本地未采用的实现不得作为已交付功能。
- 特别注意本地已有能力：例如上游新增导出，而本地早已有同等导出且最终仍保留旧实现，不应宣传为公司本月首次获得导出功能。
- 仅做公告事实整理，不自动扩展成安全审计或业务修改；如果确需审查认证、计费用量或任务插件实现，先满足仓库相应的强制阅读要求。

## 筛选与措辞

- 优先保留员工实际能感知的额度展示、选模型、生图、对话、个人资料、通知、页面交互及稳定性变化；同一功能的多次提交合并成一个条目。
- 用“在什么场景下，现在可以怎样做”描述效果，不逐条翻译 commit，不堆框架名、字段名、代码重构或依赖版本。没有测量证据不写速度提升百分比、节约金额或“彻底解决”。
- 普通员工、BP/部门负责人、管理员和超级管理员的能力分开说明。不能把超级管理员可见的 Token 汇总或缓存命中率写成全员可用。
- 区分“新增能力”和“改进已有功能”；尤其不要把额度展示优化写成增加配额，把运营结算标签写成新增支付方式，把“模型适配/内置价格”写成公司已开放该模型。
- 标注角色、开关、渠道、公司配置、插件安装等生效条件。公司是否实际开启未知的能力放入条件项，不混进已上线主清单。
- 员工需要知道的变化不能漏掉，例如旧浏览器对话历史清理、入口迁移、功能移除或需要调整客户端。技术风险、生产核对事项留给公告编辑者，不用大段实现细节占据公告正文。
- 纯格式化、内部工具/技能维护、测试调整、无可见效果的依赖升级不单列公告。必要时简短说明筛选边界，不把提交数等同于功能数。

## 交付

生成两份内容，用户指定格式或位置时优先遵循；需要落盘且未指定位置时，保存到仓库 `changes/announcements/`，以日期范围命名，已有文件不覆盖用户编辑。不要改写二开 `changes/CHANGELOG.md`，不要在 `docs/` 或任务插件目录生成公告。

1. **功能更新清单**：开头列统计范围、BASE/TARGET、代码与生产的确认状态；按读者归类。每项包括变化类型、用户价值、使用入口、适用条件及代表提交/目标代码路径。附简短的排除说明、待核实事项与实际执行的取数/检查命令。没有运行验证就不要复制旧文档的“构建通过”作为本次结果。
2. **公司公告草稿**：保留中文标题，正文直接以功能亮点的有序列表开始，不写称呼或开场引言；每项提供可操作入口，不出现 SHA、代码路径、管理员专属指标或技术维护清单。通常控制在 500～900 字，按实质变化调整。必要的使用变化单独提醒。发布状态未知时明确标注草稿及待部署核实，不虚构上线时间、公司链接或联系人。

### 公司公告草稿格式

- 页面、功能和入口名称直接写出，不使用直角引号或装饰性括号包裹。
- 功能亮点使用真正的 Markdown 有序列表，按 `1.`、`2.`、`3.` 依次编号；序号放在加粗标记外，例如 `1. **额度展示优化**`，不要写成 `**1. 额度展示优化**`。
- 每个有序列表项下的说明拆成无序列表，使用 `-`，统一缩进四个空格。每点说明一个变化、入口、条件或使用提醒，不在编号下面堆放未分点的段落。
- 有序列表标题可以加粗，但其下无序列表的分点内容不使用加粗，包括“使用提醒”等提示标签。
- 公告列表内部不留空行：有序列表项之间、有序标题与其无序子列表之间、无序子列表项之间均连续换行。保留 Markdown 标记后的必要空格及子列表的四空格缩进。
- 不写“各位同事”或“本期更新主要围绕”等开场文字。标题和草稿状态提示之后直接进入有序列表。
- 结尾说明独立于列表，与最后一个列表项之间保留一个空行，并将整段结尾加粗；结尾不缩进。
- 文档中不附加“编辑备注”“正式发送时删除”、条目删改建议或发送状态等内部编辑说明，也不将这些备注搬到其他交付文档。公告在加粗结尾处结束，不追加分隔线或备注区；如有必要的编辑沟通，仅在对话中简短说明。

示例：

```markdown
1. **额度展示优化**
    - 在概览中查看高级模型额度的已用百分比和进度条。
    - 本次优化不改变原有额度。
2. **模型选择更方便**
    - 在模型广场按输入、输出或按次价格排序。
    - 具体模型以账户可见列表为准。

**各功能的可见范围以账户权限和公司实际配置为准。欢迎从概览、模型广场查看相关变化。**
```

交付前核对每个公告亮点能回溯到清单，生效条件没有丢失，移除/回退内容未被宣传，已有功能未重复当作新增，并检查上述公告格式。没有实质用户变化时如实说明，不凑满条数。

生成清单或草稿不意味着获准群发；仅在用户明确要求发送并确定渠道、接收范围后使用对应服务工具。
