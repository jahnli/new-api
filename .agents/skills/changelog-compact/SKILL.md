# 精简二开变更日志

将 `changes/` 整理为当前有效的本地定制清单，便于理解和保护二开功能。文字简洁，关键逻辑完整；历史尝试和已撤销的中间状态通过 Git 查询。

## 范围

- 默认整理整个 `changes/CHANGELOG.md` 及关联的 `changes/details/`；用户指定编号、功能或日期范围时按其范围处理，必要时读取范围外记录核实前后关系。
- 只修改相关日志、详情和指向它们的 `changes/` 内引用，不修改业务代码、测试、技能或项目规范，不创建额外归档、整理报告或新的功能编号。
- 用户只要求预览、建议或润色方案时，只输出方案；要求精简或直接调用本技能时，完成调查后直接编辑，不逐条请求确认。
- 保留用户已有修改；默认不暂存、不提交、不推送。遵循当前任务明确授权，不因其他技能默认流程扩大操作范围。

## 核实依据

先检查 Git 状态，完整读取主索引；按功能分组读取相关详情全文，包括“新增”“调整”“移除”和同义改名记录。日志中的说明是待核实的材料，不能替代当前代码事实。

以当前本地有效代码为准，兼顾已暂存和未暂存的相关改动。结合入口、调用方、配置及 Git 历史，确认功能实际存在、被替代、部分撤销还是完全撤销。路径不存在时先查搬迁、重命名和替代实现；不能只凭关键词未命中、标题含“移除”或文件删除就判断功能消失。

涉及“是否仍是二开差异”时，确认仓库的实际上游来源，以及当前本地已集成的上游提交，固定提交标识再比较。可用 `git log --all -- <path>`、`git show <commit>:<path>`、`git diff <base> <local> -- <path>` 等只读命令取证。不要把尚未集成的最新远端状态当成当前基线，也不要仅为整理日志执行合并或改写历史。

缺乏足够证据的内容保留原文并在交付中单独说明，不猜测删除或写成已验证。读取代码不等于运行验证；不得为本次文档整理新增、修改或运行测试。

## 合并与消除规则

按业务能力及实际行为识别同一功能，不能仅因共用文件或 feature 目录就合并权限、计费、界面等不同主题。

| 情况 | 处理 |
| --- | --- |
| 本地新增 A，后续完全移除 A，当前相对上游无有效差异、无遗留影响 | 同时删除新增及移除的描述；整条只涉及 A 时删除整条 |
| A 包含多个能力，仅一部分被撤销 | 从索引与详情中去掉撤销部分，保留其他能力；不要删除整条 |
| A 经多次改名、重构、调整参数或替换为 B | 写当前名称、实现和最终行为，去掉过时的中间过程；必要的兼容映射保留 |
| 本地移除了上游原有能力 | 保留“移除”的记录，这是仍有效的二开差异；不能与本地新增后撤销混同 |
| 功能撤销后仍有数据迁移、旧值转换、遗留字段、兼容接口或部署要求 | 去掉已撤销功能的展示，只保留经核实仍影响当前运行或升级的约束 |
| 上游已完整覆盖某项本地功能 | 只有确认本地已集成对应上游代码，且行为、权限、默认值和兼容语义等价时，才移除不再存在的二开差异；仍有本地差异则保留 |
| 同一功能分散在多条或多次追加中 | 合并为当前有效的一条；不同角色、模式和适用条件不得被概括丢失 |
| 纯上游同步、冲突处理或合并过程记录 | 从二开清单清除，不转存为另一条二开记录 |

例如：本地先加“导出 PDF”，后又全部移除且无遗留影响，两次变动都不再展示。如果同条还包括有效的 Excel 导出，则仅保留 Excel。删除历史中心 BP 角色后，若当前仍执行 `role=3 → role=2` 的升级转换，则保留该兼容要求，不能将整个角色功能记为无差异。

## 精简文字

主索引使用简洁中文概括“功能 + 当前行为 + 必要条件”，通常一到两句；复杂功能可用分号连接，不能为了字数删除关键规则。

- 优先保留：适用角色和模式、权限边界、默认值、配置入口、关键限制、异常与回退、计费口径、持久化行为、迁移和兼容要求。
- 删除：同义重复、逐次追加的修改过程、已失效方案、无独立意义的样式微调数值、重复的文件清单，以及“完善、增强、优化”等没有具体行为的信息。
- 将“先新增 X，随后调整 X，最后改为 Y”改为最终有效的 Y；不要用“统一处理”“体验优化”等泛化措辞替换实际规则。
- 详情按现有功能和约束组织，同一能力的历史小节合并；保留必要的实现入口及其职责，不逐文件重复同一句说明。不强制所有详情采用同一模板。
- 关键枚举值、环境变量、接口路径、数量或精度限制在仍影响理解或复核时保留；不能擅自修正业务值，也不能将历史构建结果写成当前验证结果。

示例：

> 原：新增后台开关；后续改为环境变量，删除开关；调整字段展示，并修复旧配置生效问题。
>
> 精简：对外模式由 `EXTERNAL_MODE` 控制，默认关闭，忽略旧数据库配置；前后端按模式隐藏内部资料。

示例仅说明写法，实际保留内容必须从代码核实。

## 编号、日期与详情维护

- 保留已有三位编号，不重新连续编号，不将删除条目的编号分配给其他功能；允许编号空缺。
- 多条合并时优先保留仍代表该业务主题的原编号，其他编号移除；修复 `changes/` 内受影响的引用。仓库其他地方仍引用旧编号时，交付中列出，不能悄悄删成断链或越界修改。
- 纯文案整理不把日期更新为整理当天。合并条目时使用有依据的、与最终保留行为有关的最新业务变更日期；表格和详情日期保持一致。无法核实时保留已有日期并说明。
- 索引、详情标题、正文和文件清单必须一致；删除的功能不能继续在详情中呈现为有效能力，也不在别处保留“曾新增、现已删除”的重复历史段落。
- 已迁移路径仅在确认对应关系后更新；跨层关键入口可以保留，重复语言文件可按真实语言集合归并，不擅自补称七语言已完成。
- 整条删除后，仅在确认对应详情专属于该条、无剩余有效内容且无其他引用时删除详情。共享详情只删对应段落；仅凭“未被索引链接”不足以删除文件。
- 不新增墓碑条目或单独的删除清单来替代已消除的功能。Git 历史已经保存原始记录。

## 完成检查与交付

检查修改后的索引与详情：保留的每项关键逻辑有依据，取消内容已同步消除，编号唯一且不重排，Markdown 表格及相对链接有效，删除详情无残留引用。使用 `git diff --check` 和实际 diff 检查格式及改动范围；只做文档静态检查，不触发业务构建或测试。

交付时简要列出：压缩了哪些主题、哪些记录被合并、哪些新增后撤销的内容被消除、仍保留的关键兼容约束，以及未能核实或存在外部引用的项目。不能仅报告减少了多少字，更不能将仅完成措辞压缩表述为已核实全部二开差异。
