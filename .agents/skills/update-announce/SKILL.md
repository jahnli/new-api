# 功能更新公告

## 目标与边界

- 根据项目已提交的实际变化，整理面向使用者的中文功能更新清单，可用于更新公告、上线公告或近期更新汇总。
- 默认只读分析 Git 历史与相关文件，不修改代码、CHANGELOG 或版本号，不提交、推送、发布或部署。不把工作区未提交改动算作更新。
- 遵循仓库 AGENTS.md；需要深入核实特定领域行为时，先读取该领域要求的规则。

## 日期与来源

1. 在执行时获取当前日期、时间和本地时区，不使用本文或历史对话中的固定日期。
2. 按用户提供的信息确定范围：
   - 明确起止日期：包含起止两天；内部按起始日零点到结束日次日零点的左闭右开区间处理。
   - 单个日期或“从某日开始”：默认从该日零点到当前时刻；“某日当天”仅统计该日。
   - 指定月份：统计该自然月；“最近 N 天”“本周”“上个月”等按明确语义计算。
   - 未提供日期：默认从当前时刻向前推一个自然月到当前时刻；目标月份没有对应日期时取该月最后一天，不将一个月固定等同于 30 天。
   - 范围结束时间晚于当前时刻时，以当前时刻为截止。缺少年份时采用当年并在输出中写出完整日期；存在多种合理解释或起止倒置时才询问。
3. 核实 Git 仓库根目录、当前分支和 HEAD。默认分析当前 HEAD 可达的历史；用户指定分支、标签或版本时，使用指定来源，并固定其提交 ID。
4. 核实历史是否完整。不是 Git 仓库、指定引用不存在或浅克隆缺少必要历史时，明确说明限制；不能用猜测的功能补齐公告，也不能把缺少历史当作没有更新。
5. 在公告的更新范围行中只写实际起止日期，只有范围边界需要时才补充时间和时区。来源分支、版本和固定提交仅用于内部核实，默认不展示；用户明确要求追溯时再提供。

## 提交调查与核实

1. 使用 Git 只读命令查看状态、历史与差异，例如 `git status --short`、`git rev-parse HEAD`、`git log`、`git show`、`git diff`。完整遍历所需范围，不以最近若干条提交代替完整清单。
2. 默认以提交者时间判断日期，使用带时区的时间值。可用 `git log --format="%H %P %cI %s" <固定提交>` 收集候选，再按区间核对；不依赖作者时间或提交标题推断发布时间。
3. 对合并提交，以其相对第一父提交的实际差异核实本次接入的功能。即使上游原始提交早于起始日期，只要在范围内首次合入目标分支，也应纳入本次接入内容；不要同时重复列出合并提交与子提交中的同一功能。
4. 阅读候选提交的说明、受影响文件及关键差异，必要时核对调用方和范围截止时的代码。可参考 `changes/CHANGELOG.md` 及相关详情，但 Git 实际结果优先；公告既可包含二开，也可包含实际接入的上游功能。
5. 合并同一功能的多次提交、修正和补充。检查撤销、替代与后续修复；期间新增又完全撤销的功能不列为新增，功能替代按最终行为描述。
6. 只写有证据的行为变化。提交标题不能单独证明功能完成、性能提升比例、支持范围或生产部署状态。历史范围按截止时状态汇总，不把截止之后的功能混入。用户明确提供的模型公告、价格调整或推荐建议可作为补充来源；不能将其伪称为 Git 已实现的变化。
7. 在分析中保留每项公告对应的提交和文件依据；默认不把哈希、内部路径及调查过程放进公告。用户要求追溯时，再以无序列表附上来源。

## 内容整理

- 优先写新增功能、使用体验改善、重要问题修复，以及需要用户采取行动的兼容性或配置变化。
- 先提取 Highlights，再将剩余变化按 Feat、Fixes、Perf 分类，在各类内按功能或使用场景合并；重要内容优先，不按提交时间机械罗列。
- 每项说明“新增或改善了什么、用户可以怎样使用或解决了什么问题”；适用角色、使用入口、配置前提有证据时才补充。
- 用明确、简洁的中文，不直接照抄 commit message，不使用空泛的“全面优化”“大幅提升”等措辞。
- 纯格式调整、内部重构、测试、CI、开发工具或依赖版本变动，若无明确用户影响，默认省略。确有兼容性或操作影响时，说明具体影响。
- 不将“代码已合入”写成“已上线”。缺少部署证据时使用中性功能表述；用户要求上线公告也不能自行编造上线时间、版本号或可用状态。
- 默认不展示“来源：v1 分支已提交内容”等来源说明，也不添加“本清单汇总期间实际合入的功能变化，具体可用情况以所用环境的部署版本和配置为准。”等部署状态或可用性免责声明。
- 无符合条件的功能更新时，保留标题与范围，并用列表明确写“该时间范围内暂无可确认的功能更新”；不填充无关提交。

## 更新分类

- Highlights：需要优先关注的更新，包括模型新增、模型下架、模型价格变动、模型推荐、使用建议，以及用户明确要求重点标记的其他变化。
  - 模型新增说明模型名称、能力与适用入口；模型下架说明影响范围，有依据时补充替代模型、迁移方式及生效日期。仅从内置候选列表删除名称不等于模型下架。
  - 模型价格变动说明涉及模型、计价单位和适用范围；调整前后价格、币种、生效时间仅在有明确依据时填写。定价编辑器、价格展示或同步工具的功能改进仍归 Feat，不当作实际模型调价。
  - 推荐与建议依据用户明确提供的内容或已核实的项目变化，说明适用场景、推荐理由及必要前提；不得为了填充 Highlights 自行编造推荐、价格、下架计划或可用状态。
- Feat：未纳入 Highlights 的新增或扩展能力、入口、配置或接口支持；正常功能的交互与展示改善也归入此类。模型新增统一放入 Highlights。
- Fixes：修复已有功能的错误、兼容问题或异常行为，说明原先的问题及修复后的表现。已有功能的独立修复单独归类，不因属于同一模块而并入 Feat；仅为本期新功能补齐实现的连续修正，合并为该功能的最终行为。
- Perf：有实际差异依据的响应速度、吞吐、内存、网络、查询或并发效率改善，说明受影响的场景和具体变化。不能仅凭 perf 提交前缀或“优化”措辞归类；布局、文案及普通重构不算性能改进，没有测量依据不写提升比例。
- 按最终用户行为分类，不直接照搬提交前缀；同一提交包含不同类型变化时可以拆分，同一变化只出现一次。Highlights 优先且独占：已在 Highlights 展示的内容不得再在 Feat、Fixes、Perf 中重复，不以改写措辞或摘要方式重复列出；同一模块中不同的独立变化仍可分别归类。
- 需要用户采取行动的配置或兼容性变化并入所属条目；已纳入 Highlights 的建议与迁移说明随该条目保留，其余按新增能力、修复问题或改善性能分类，不另设“更新注意事项”。
- 分类顺序固定为 Highlights、Feat、Fixes、Perf，无内容的分类省略，不填充占位项；所有分类均无内容时使用前述无更新提示。

## 交付格式（强制）

1. 默认将完整公告的 Markdown 源码放入一个标注为 `markdown` 的代码块，不附分析过程或重复的渲染版本。目标是公告页面的 Markdown 输入框，由该编辑器渲染后用于飞书；使用代码块的复制按钮保留 `**`、无序列表标记和嵌套缩进，仅复制块内内容，围栏不属于公告。不要让用户从聊天界面的渲染正文复制到 Markdown 输入框，这会丢失加粗标记。用户明确要求富文本正文时，才改为直接渲染且不包代码块；明确要求保存文件时再写入指定位置。
2. 更新范围放在公告最顶部，作为第一行独占一行，写作“更新范围：YYYY-MM-DD 至 YYYY-MM-DD”，日期按实际统计区间填写。空一行后显示固定标题“AI Gateway 功能更新公告”，以 `**AI Gateway 功能更新公告**` 加粗并独占一行，不添加 `#`、`##` 等 Markdown 标题前缀。
3. 标题下方使用两级 Markdown 无序列表，按顺序输出有内容的分类。分类写作 `- **Highlights**`、`- **Feat**`、`- **Fixes**`、`- **Perf**`，各自独占一行，不添加数字序号。每个分类下的条目前缩进两个空格，以 `  - ` 开头，形成真正的嵌套列表；折行续写时与该条目的正文起始列对齐。每条写作“功能或场景名称：具体变化及用途或影响”，不手写 `•` 字符。不能只在独立分类段落后的顶层列表前添加空格，那不会建立列表层级；也不要用全角空格模拟缩进。全范围无更新时，直接输出一条无序列表提示，不套空分类。
4. 更新范围、标题和各分类之间留空行，分类标题与其无序列表之间也留空行，同类条目连续排列。仅主标题与分类标题加粗，更新范围与说明条目使用普通文字。不使用表格、引用块、任务复选框、图表、HTML 或除上述加粗与列表之外的 Markdown 样式。不输出“更新注意事项”分区；必要的配置前提或兼容性说明简洁并入对应条目。
5. 下方模板仅说明格式，必须替换占位符并按实际内容增删，不得把示例当作真实更新。

下方示例展示默认交付的 Markdown 源码：

```markdown
更新范围：YYYY-MM-DD 至 YYYY-MM-DD

**AI Gateway 功能更新公告**

- **Highlights**

  - 模型或重点事项名称：经核实的新增、下架、价格变化或推荐建议及适用范围。

- **Feat**

  - 功能或场景名称：新增的能力及其具体用途。

- **Fixes**

  - 功能或场景名称：原先的问题及修复后的表现。

- **Perf**

  - 功能或场景名称：有差异依据的性能改善及适用范围。
```

## 调用示例

- `/update-announce`：整理最近一个自然月的功能更新。
- `/update-announce 2026-10-01 至 2026-10-31`：整理指定日期范围内的功能更新。
- `/update-announce 从 2026-10-15 开始，用于上线公告`：整理该日起至当前时刻的更新，采用上线公告的文案风格。
- `/update-announce 上个月，面向普通用户`：整理上个自然月的更新，优先呈现普通用户可感知的变化。

## 交付前复核

- 日期、时区、来源和历史完整性已核实，默认范围为最近一个自然月。
- 每项均有 Git 差异依据，合并带入的功能未遗漏，重复和撤销内容已处理。
- 已先提取 Highlights，再按实际行为区分 Feat、Fixes、Perf；模型新增、下架、价格变动和推荐建议已按规则归入 Highlights，且没有在其他分类重复。独立修复未混入新增功能，性能描述有证据且未夸大；无内容分类已省略。
- 未把未提交内容或未经证实的部署状态写成已发布功能。
- 默认输出不包含来源说明或部署状态、可用性免责声明。
- 默认输出为单个 Markdown 代码块中的完整源码，主标题与分类标题保留字面量 `**`，不得用渲染正文替代；用户明确要求富文本时才直接渲染。块内第一行为实际更新范围，空一行后为固定标题“AI Gateway 功能更新公告”；分类为不带数字序号的加粗无序列表项，具体变化以两个空格缩进为其子列表，确保渲染后比分类缩进一级。更新范围与说明条目未加粗，不输出“更新注意事项”分区；无手写 `•` 字符、Markdown 标题前缀或占位符。
