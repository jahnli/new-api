# 功能更新公告

## 目标与边界

- 根据项目已提交的实际变化，整理面向使用者的中文功能更新清单，可用于更新公告、上线公告或近期更新汇总。
- 默认只读分析 Git 历史与相关文件，不修改代码、CHANGELOG 或版本号，不提交、推送、发布或部署。不把工作区未提交改动算作更新。
- 遵循仓库 AGENTS.md；需要深入核实特定领域行为时，先读取该领域要求的规则。

## 日期与来源

1. 在执行时获取当前日期、时间和本地时区，不使用本文或历史对话中的固定日期。
2. 按用户提供的信息确定范围：
   - 明确起止日期：包含起止两天；内部按起始日零点到结束日次日零点的左闭右开区间处理。
   - 单个日期或“从某日开始”：默认从该日零点到当前时刻；“某日当天”仅统计该日。
   - 指定月份：统计该自然月；“最近 N 天”“本周”“上个月”等按明确语义计算。
   - 未提供日期：默认从当前时刻向前推一个自然月到当前时刻；目标月份没有对应日期时取该月最后一天，不将一个月固定等同于 30 天。
   - 范围结束时间晚于当前时刻时，以当前时刻为截止。缺少年份时采用当年并在输出中写出完整日期；存在多种合理解释或起止倒置时才询问。
3. 核实 Git 仓库根目录、当前分支和 HEAD。默认分析当前 HEAD 可达的历史；用户指定分支、标签或版本时，使用指定来源，并固定其提交 ID。
4. 核实历史是否完整。不是 Git 仓库、指定引用不存在或浅克隆缺少必要历史时，明确说明限制；不能用猜测的功能补齐公告，也不能把缺少历史当作没有更新。
5. 在公告的更新范围行中只写实际起止日期，只有范围边界需要时才补充时间和时区。来源分支、版本和固定提交仅用于内部核实，默认不展示；用户明确要求追溯时再提供。

## 提交调查与核实

1. 使用 Git 只读命令查看状态、历史与差异，例如 `git status --short`、`git rev-parse HEAD`、`git log`、`git show`、`git diff`。完整遍历所需范围，不以最近若干条提交代替完整清单。
2. 默认以提交者时间判断日期，使用带时区的时间值。可用 `git log --format="%H %P %cI %s" <固定提交>` 收集候选，再按区间核对；不依赖作者时间或提交标题推断发布时间。
3. 对合并提交，以其相对第一父提交的实际差异核实本次接入的功能。即使上游原始提交早于起始日期，只要在范围内首次合入目标分支，也应纳入本次接入内容；不要同时重复列出合并提交与子提交中的同一功能。
4. 阅读候选提交的说明、受影响文件及关键差异，必要时核对调用方和范围截止时的代码。可参考 `changes/CHANGELOG.md` 及相关详情，但 Git 实际结果优先；公告既可包含二开，也可包含实际接入的上游功能。
5. 合并同一功能的多次提交、修正和补充。检查撤销、替代与后续修复；期间新增又完全撤销的功能不列为新增，功能替代按最终行为描述。
6. 只写有证据的行为变化。提交标题不能单独证明功能完成、性能提升比例、支持范围或生产部署状态。历史范围按截止时状态汇总，不把截止之后的功能混入。
7. 在分析中保留每项公告对应的提交和文件依据；默认不把哈希、内部路径及调查过程放进公告。用户要求追溯时，再以渲染后的无序列表附上来源。

## 内容整理

- 优先写新增功能、使用体验改善、重要问题修复，以及需要用户采取行动的兼容性或配置变化。
- 按功能或使用场景组织，相关修复并入对应功能；重要内容优先，不按提交时间机械罗列。
- 每项说明“新增或改善了什么、用户可以怎样使用或解决了什么问题”；适用角色、使用入口、配置前提有证据时才补充。
- 用明确、简洁的中文，不直接照抄 commit message，不使用空泛的“全面优化”“大幅提升”等措辞。
- 纯格式调整、内部重构、测试、CI、开发工具或依赖版本变动，若无明确用户影响，默认省略。确有兼容性或操作影响时，说明具体影响。
- 不将“代码已合入”写成“已上线”。缺少部署证据时使用中性功能表述；用户要求上线公告也不能自行编造上线时间、版本号或可用状态。
- 默认不展示“来源：v1 分支已提交内容”等来源说明，也不添加“本清单汇总期间实际合入的功能变化，具体可用情况以所用环境的部署版本和配置为准。”等部署状态或可用性免责声明。
- 无符合条件的功能更新时，保留标题与范围，并用列表明确写“该时间范围内暂无可确认的功能更新”；不填充无关提交。

## 交付格式（强制）

1. 最终回复直接输出渲染后的公告正文，不包裹代码块，不交付 Markdown 源文，不附分析过程或重复版本。使用者可选中渲染后的正文复制，以保留编号及嵌套列表结构并粘贴到飞书输入框。用户明确要求保存文件时再写入指定位置。
2. 更新范围放在公告最顶部，作为第一行独占一行，写作“更新范围：YYYY-MM-DD 至 YYYY-MM-DD”，日期按实际统计区间填写。空一行后显示固定标题“AI Gateway 功能更新公告”，标题使用普通文字独占一行，不添加 `#`、`##` 等 Markdown 标题前缀，也不使用 `**` 等加粗标记。
3. 标题下方的功能大项使用连续编号的 Markdown 有序列表；功能说明使用该项下的 Markdown 嵌套无序列表，以 `- ` 作为源文标记，由聊天界面渲染成列表，不手写 `•` 字符。嵌套列表按所属编号的正文起始列缩进，保证两位数编号下仍保持正确层级。
4. 更新范围、标题和各功能大项之间留空行，编号项与其嵌套无序列表之间也留空行，同一功能的说明连续排列。不使用表格、引用块、任务复选框、图表、HTML 或列表以外的 Markdown 样式。不输出“更新注意事项”分区；必要的配置前提或兼容性说明简洁并入对应功能的说明列表。
5. 下方模板仅说明格式，必须替换占位符并按实际内容增删，不得把示例当作真实更新。

下方示例直接展示预期的渲染格式：

更新范围：YYYY-MM-DD 至 YYYY-MM-DD

AI Gateway 功能更新公告

1. 功能或使用场景名称

   - 新增的能力及其具体用途。
   - 相关体验改善或已修复的问题。

2. 另一项功能或使用场景名称

   - 实际变化及适用范围。

## 调用示例

- `/update-announce`：整理最近一个自然月的功能更新。
- `/update-announce 2026-10-01 至 2026-10-31`：整理指定日期范围内的功能更新。
- `/update-announce 从 2026-10-15 开始，用于上线公告`：整理该日起至当前时刻的更新，采用上线公告的文案风格。
- `/update-announce 上个月，面向普通用户`：整理上个自然月的更新，优先呈现普通用户可感知的变化。

## 交付前复核

- 日期、时区、来源和历史完整性已核实，默认范围为最近一个自然月。
- 每项均有 Git 差异依据，合并带入的功能未遗漏，重复和撤销内容已处理。
- 未把未提交内容或未经证实的部署状态写成已发布功能。
- 默认输出不包含来源说明或部署状态、可用性免责声明。
- 输出为直接渲染的公告正文，无代码块；第一行为实际更新范围，空一行后为固定标题“AI Gateway 功能更新公告”；功能连续编号，功能说明正确渲染为编号项下的嵌套无序列表，不输出“更新注意事项”分区；无手写 `•` 字符、Markdown 标题前缀、加粗标记或占位符。
