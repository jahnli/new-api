# 上游合并后复盘与上线交接

## 目标

对已经完成的 upstream 合并进行可追溯复盘，回答五个核心问题：

1. 有哪些改动；
2. 合并了哪些内容；
3. 影响到了哪些本地功能；
4. 上线前需要关注哪些行为变化；
5. 哪些部分需要人工测试。

报告必须描述最终运行行为，而不是简单复述 commit message 或罗列文件。

## 适用时机

在以下场景使用：

- upstream 合并提交已经创建，需要交付影响报告；
- 用户要求检查最近一次上游同步、冲突解决或二开影响；
- 上线前需要从合并内容生成手工验收清单；
- 合并已经推送，但需要补充发布说明或回归范围。

若合并尚未完成、仍有冲突或待确认文件，返回 `upstream-merge` 流程，不得提前生成“最终影响”结论。

## 硬性规则

1. **默认只读**：复盘请求不授权修改代码、CHANGELOG、提交、推送或部署。
2. **以 Git 和最终代码为准**：commit message 只作为线索，不能代替 diff、调用方和测试核实。
3. **固定三方视角**：始终区分共同基线、合并前本地版本、上游版本和最终合并结果。
4. **本地功能优先追踪**：必须读取 `changes/CHANGELOG.md`，并读取所有与重叠文件相关的 `changes/details/*.md`。
5. **不把文件重叠等同于功能受损**：必须检查最终代码后再判定“保留、增强、行为改变、待验证或丢失”。
6. **不把构建通过等同于业务正确**：自动验证与人工验收必须分开报告。
7. **不虚构验证结果**：未实际执行的命令和人工测试只能标记为“建议/待执行”。
8. **明确破坏性变化**：涉及 API 契约、默认值、权限、计费、数据、配置、路由、兼容别名或部署参数时，必须给出迁移方式或阻塞说明。
9. **计费路径纵深检查**：只要上游触及模型身份、倍率、价格、表达式、预扣、结算或日志，必须追踪完整计费链路并核对本地计费不变量。
10. **数据库验证不降级**：若触及数据库行为，必须按根 `AGENTS.md` 报告 SQLite、MySQL、PostgreSQL 的真实验证情况；没有执行就明确列为上线阻塞或验证缺口。
11. **RelayKit 独立性**：若触及 `relaykit/`，必须单独报告 `GOWORK=off go build ./...` 和相关测试状态。

## 第一步：确定精确合并范围

优先使用用户给出的 merge commit。未给出时：

```bash
git status --short --branch
git log --merges --first-parent --max-count=10 --oneline
```

仅当最近一次合并提交与用户描述唯一吻合时才选择它；有多个候选时询问用户，不得猜测。

读取提交父级：

```bash
git rev-list --parents -n 1 <merge-commit>
```

标准双亲合并中：

- 第一个父提交 `<local-parent>`：合并前本地版本；
- 第二个父提交 `<upstream-parent>`：本次接入的上游版本；
- `<base>`：`git merge-base <local-parent> <upstream-parent>`。

若不是双亲合并：

- octopus merge：停止并询问要分析哪个父级；
- squash/cherry-pick：要求用户提供合并前本地提交和上游目标提交；
- 不得把 `HEAD^`、远端当前 HEAD 或日期近似值当作隐含基线。

## 第二步：建立四份证据

### 2.1 上游实际改动

```bash
git log --oneline <base>..<upstream-parent>
git diff --stat <base>..<upstream-parent>
git diff --name-status <base>..<upstream-parent>
git diff --numstat <base>..<upstream-parent>
```

记录：

- 上游提交数；
- 新增、修改、删除和重命名文件数；
- 总增删行数；
- 按目录或业务域聚合的文件与行数；
- commit body 中声明的 breaking change 和 migration。

### 2.2 合并前本地改动

```bash
git diff --name-status <base>..<local-parent>
git log --oneline <base>..<local-parent> -- <file>
```

将本地改动文件与上游改动文件求交集，得到高风险重叠文件。不要只检查 Git 显式冲突。

### 2.3 最终合并结果

```bash
git diff --stat <local-parent>..<merge-commit>
git diff --name-status <local-parent>..<merge-commit>
git show --remerge-diff --format= <merge-commit>
```

逐上游提交核对文件：

```bash
git log --format=%H <base>..<upstream-parent>
git show --stat --name-only <upstream-commit>
git diff <merge-commit> <upstream-parent> -- <file>
```

检查：

- 上游每个文件是否在最终结果中体现；
- 最终是否新增了不属于上游 diff 的手动保护、测试或生成报告；
- 冲突解决是否保留双方关键逻辑；
- 上游删除的旧实现是否仍异常残留；
- 新函数、类型、字段和配置的调用方是否完整同步。

`--remerge-diff` 只用于定位冲突解决和额外手动调整，不能代替完整三方 diff。

### 2.4 二开功能映射

完整读取：

- `changes/CHANGELOG.md`；
- 与重叠文件匹配的 `changes/details/*.md`；
- 最终版本中的重叠文件、直接调用方、相关配置

每项本地功能至少记录：

- CHANGELOG 编号和功能名；
- 合并前本地行为；
- 上游对同一文件或契约的修改；
- 最终运行行为；
- 风险等级；

若文件未写入 CHANGELOG，但包含明显本地不变量（品牌命名、锁顺序、模块独立性、权限边界等），以“本地不变量”单独列出，不得忽略。

## 第三步：按行为归纳“合并了什么”

禁止把几十个文件逐行堆给用户。将上游改动整理为端到端业务链，例如：

```text
输入/API → 鉴权 → 路由/选渠 → 映射/转换 → 计费 → 日志/审计 → UI/配置
```

每个功能域说明：

- 原先怎样运行；
- 上游新增、删除或重构了什么；
- 最终版本现在怎样运行；
- 哪些协议、角色、渠道、配置或部署方式会观察到变化；

优先识别以下变化：

- 新 API、字段、参数、模型名或配置语法；
- 默认值、优先级、fallback 和错误码变化；
- 权限范围扩大或收紧；
- 计费身份、倍率、价格、预扣和结算变化；
- 缓存键、选渠、重试和亲和策略变化；
- 透传与协议转换语义变化；
- 旧别名、兼容层或弃用路径移除；
- 数据库 schema、迁移、索引、驱动或 SQL 变化；
- UI、i18n、部署参数和环境变量变化。

## 第四步：判定本地功能影响

每项本地功能只能使用以下结论之一：

- **完整保留**：最终行为与合并前本地行为一致；
- **保留并增强**：本地行为保留，同时接入上游能力；
- **兼容性调整**：最终仍支持本地目标，但调用方式、配置或边界发生变化；
- **待人工验证**：代码看似兼容，但依赖真实上游、权限、配置、数据库或 UI 交互；
- **功能受损/丢失**：有可验证的本地行为缺失，必须明确指出，不得弱化措辞。

风险等级：

- **P0 / 高**：计费错误、越权、数据丢失、认证不可用、主要 API 中断；
- **P1 / 中**：兼容别名、路由选择、关键 UI 流程、外部服务集成变化；
- **P2 / 低**：文案、提示、内部重构且有直接自动测试覆盖。

判定“完整保留”前，至少核实最终文件、直接调用方和一项测试或可观察行为。

## 第五步：提取上线前行为变化

只列真实可观察变化，不重复内部重构。每项必须包含：

```text
[严重级别] 行为名称
- 以前：旧行为
- 现在：最终行为
- 影响对象：客户端 / 管理员 / 普通用户 / 某渠道 / 某部署
- 上线动作：无需动作 / 修改配置 / 迁移调用 / 灰度观察 / 阻塞上线
- 发现方式：请求、日志、账单、页面或数据库如何确认
```

以下情况即使测试通过也必须列入：

- breaking change；
- 默认值或 fallback 改变；
- 原来接受的输入现在返回 4xx/5xx；
- 权限集合扩大；
- 同一请求可能选择不同渠道或价格键；
- 日志或审计字段新增、删除或仅管理员可见；
- 配置格式、环境变量或迁移步骤变化。

## 第六步：生成人工测试清单

人工测试必须从“最终行为变化 + 本地重叠功能 + 自动测试盲区”推导，不能写成泛化的“全面回归”。

### 6.1 最低必测范围

至少覆盖：

1. 一个主成功路径；
2. 涉及既有行为时，一个向后兼容路径；
3. 存在 breaking change 时，每项变化的迁移前后对比；
4. 每项 P0/P1 本地重叠功能；
5. 涉及可配置行为时，配置开启与关闭各一条路径；
6. 错误输入、权限不足或 fallback 边界；
7. 日志、账单或审计结果，而不只检查 HTTP 200；
8. 涉及 UI 时，覆盖保存、回显、刷新和受影响语言展示。

### 6.2 按改动类型补充

- `relay/`、`relaykit/`：测试原生协议、跨协议、流式/非流式、透传开关、模型映射和真实上游响应；
- 计费：核对预扣、最终扣费、价格键、分组倍率、供应商倍率、日志快照和退款/差额；
- 权限：使用 Root、管理员、普通用户和受限 Token 验证允许与拒绝路径；
- 路由/缓存：分别测试内存缓存开启/关闭、精确模型、fallback、重试和亲和；
- 数据库：三库真实实例，覆盖全新库、升级库、重复迁移和数据/索引保留；
- 前端：桌面/移动端、保存/回显、错误态、禁用态、键盘可操作性和受影响语言；
- i18n：至少验证基础语言、中文 fallback 和本次冲突语言，不只检查 JSON 可解析；
- 外部集成：真实或沙箱凭据验证 OAuth、LDAP、对象存储、通知、支付等受影响链路；
- 部署：验证新增/变更环境变量、Docker 构建参数、启动日志和回滚路径。

### 6.3 每条用例格式

```text
[P0/P1/P2] 用例名称
- 保护目标：对应上游变化和本地功能编号
- 前置条件：角色、Token、渠道、模型、配置、余额/套餐、数据库或外部服务
- 操作步骤：可直接执行的请求或 UI 操作
- 预期结果：状态码、响应字段、上游请求、渠道、扣费、日志和页面状态
- 失败判定：什么现象说明合并存在回归
- 自动覆盖：已有测试名；没有则写“无”
- 人工状态：待执行 / 通过 / 失败 / 阻塞
```

优先级排序：P0 在前，再列 P1、P2。若某项已被自动测试覆盖但仍依赖真实环境，保留人工用例并说明自动测试不能替代的部分。

## 第七步：核对自动验证

从实际终端输出或 CI 结果记录验证，不凭记忆。按变更范围检查：

- 根模块构建和相关/完整 Go 测试；
- `relaykit/` 独立构建与测试；
- 前端 typecheck、涉及文件 lint、相关测试和生产构建；
- i18n 同步报告；
- 数据库三方言矩阵；
- 每个上游提交的文件完整性。

输出分为：

- **已执行并通过**；
- **已执行但失败**；
- **未执行/受阻**；
- **仍需人工验证**。

不得将“建议运行”写成“已验证”。

## 最终报告模板

```markdown
# 上游合并复盘

## 执行摘要

- 合并提交、上游范围和共同基线
- 文件数、增删量、冲突数和手动调整数
- 本地功能总体结论
- 最高风险与上线建议

## 1. 有哪些改动

- 提交和文件规模
- 按业务域汇总改动
- 新增、修改、删除、重命名和依赖/数据库情况

## 2. 合并了哪些内容

### [功能域]
- 合并前行为
- 上游修改
- 最终行为
- 关键证据

## 3. 影响到了哪些本地功能

### #[编号] [功能名] — [完整保留/保留并增强/兼容性调整/待人工验证/功能受损]
- 合并前本地逻辑
- 上游修改逻辑
- 最终合并逻辑
- 风险等级
- 证据与测试

## 4. 上线前关注的行为变化

### [P0/P1/P2] [行为名称]
- 以前
- 现在
- 影响对象
- 上线动作
- 验证方式

## 5. 人工测试清单

### [P0/P1/P2] [用例名称]
- 保护目标
- 前置条件
- 操作步骤
- 预期结果
- 失败判定
- 自动覆盖
- 人工状态：待执行

## 6. 自动验证与缺口

- 已通过
- 失败
- 未执行/阻塞
- 数据库、真实上游或外部服务验证缺口
```

## 交付前自检

- [ ] 精确识别 merge commit、两个父提交和共同基线；
- [ ] 上游提交和文件无遗漏；
- [ ] 所有重叠文件都关联到 CHANGELOG 或本地不变量；
- [ ] 每项本地功能都说明最终运行逻辑；
- [ ] breaking change 有迁移方案；
- [ ] 计费、权限、数据库和透传边界单独检查；
- [ ] 人工测试包含前置条件、步骤、预期和失败判定；
- [ ] 自动验证与人工待测状态没有混淆；
- [ ] 未执行验证和阻塞项明确披露；
- [ ] 报告引用关键文件、提交或测试作为证据。
